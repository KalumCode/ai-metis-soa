# 架构设计规范

> 来源：《架构设计规范》。以下规则在生成技术方案时**必须遵守**。

---

## 一、架构原则

### 1. 应用架构设计原则

| 原则 | 规则要求 |
|------|----------|
| **稳定优先** | 稳定高于一切，以稳定为中心，不过度设计 |
| **合适简单** | 合适优于业界领先；简单优于复杂——两种方案都可满足要求时，选择简单方案 |
| **演化迭代** | 演化优于一步到位，不贪大求全；架构需与业务目标一致，不符合业务的架构再领先也没用 |
| **解耦拆分** | 按业务或功能分离应用；稳定部分与易变部分分离；服务与实现细节分离 |
| **抽象化** | 应用只依赖服务抽象，不依赖服务实现细节和位置；数据层只依赖逻辑数据库 |
| **集成规范** | 提供RESTful风格API接口；易变依赖稳定，非核心依赖核心服务；充分利用公司信息化基础设施，避免重复设计开发 |
| **柔性适应** | 能够敏捷适应业务发展，避免因业务流程改变导致系统大规模调整 |
| **可治理** | 服务自治、SLA、可水平扩展、可限流、可降级、服务白名单 |

### 2. 数据架构设计原则

| 原则 | 规则要求 |
|------|----------|
| **标准化** | 数据标准化：及时性、一致性、准确性、完整性 |
| **解耦隔离** | 访问量大的数据库做读写分离；数据量大的数据库做分库分表；不同业务域数据库做分区隔离 |
| **服务访问** | 数据库通过服务访问，避免直接访问其他宿主的数据库 |
| **统一治理** | 统一元数据管理、统一主数据管理 |
| **容灾治理** | 重用数据做主备；双写要做补偿；合理利用缓存容灾；服务集群部署避免单点故障 |
| **缓存原则** | 热点数据应做好缓存预加载；需处理缓存雪崩、缓存击穿 |

### 3. 技术架构设计原则

| 原则 | 规则要求 |
|------|----------|
| **DID原则【强制】** | 设计10倍容量→ 实现3倍容量→ 部署1.5倍容量 |
| **N+1部署** | 避免单点，采用 N+1 部署原则 |
| **可治理** | 可监控、可容灾、可容错、故障转移、安全保障、支持在线扩容、灰度发布、版本可回滚 |
| **虚拟化部署** | 服务器资源抽象，应用只依赖虚拟化资源 |

### 4. 评审八大原则（每条10分，60分以上合格）

1. **清晰性**：架构应易于理解和解释，清晰传达设计意图
2. **可靠性**：处理异常情况，具有错误处理和恢复机制
3. **可扩展性**：适应未来需求变化和增长，减少系统重构
4. **性能**：处理大量数据和并发请求，保持低延迟
5. **安全性**：保护系统免受安全威胁和攻击
6. **可维护性**：方便修改、扩展和维护
7. **可测试性**：方便进行单元测试、集成测试和系统测试
8. **可重用性**：公共功能和模块进行抽象和封装，可重复使用

## 二、技术选型规范

### 强制要求

- **成熟稳定**：选择经过广泛验证、成熟稳定的技术栈，避免使用过于新颖或未经充分验证的技术
- **横向对标**：选型前必须对比业界3个以上组件；有国产化要求时优先使用国产化；尽量使用基于 Apache 3.0 协议开源的
- **社区支持**：选择有良好社区支持、可持续性强的技术和框架
- **偏差处理**：对技术选型的任何偏差，应启动偏差流程上报项目管理组，批准后方可执行

### 公司标准技术栈

| 类别 | 技术选型 |
|------|----------|
| 缓存 | Redis 主从模式 |
| 消息队列 | RocketMQ |
| 关系型数据库 | MySQL 主备 |
| 配置中心 | Nacos |
| RPC框架 | Dubbo |
| 监控平台 | Skywalking |
| 日志平台 | ELK |
| 应用容器 | Undertow |
| 定时任务 | XXL-Job |
| 负载均衡 | Nginx |
| 规则引擎 | Drools |
| 文件系统 | OSS |
| 协调服务 | Zookeeper |
| 本地缓存 | Ehcache |
| 非关系型数据库 | MongoDB |
| 熔断限流 | Sentinel |
| JDK | JDK 21 |

## 三、数据表设计规范

- 新建表和库需提供 ER 图
- MySQL 数据量达到 500-800 万需考虑分库分表
- 分库策略：垂直分库，按业务领域（财务、支付、订单、产品等）
- 主键采用雪花算法生成

---

## 四、接口设计规范

- 提供 RESTful 风格 API 接口
- 接口设计需包含：接口名称、描述、请求URI、请求Body、响应Data、数错误码

---

## 五、非功能特性设计要点

生成技术方案时，应根据业务场景评估以下非功能需求：

| 维度 | 关键考虑点 |
|------|-----------|
| **高并发** | 负载均衡（多级均衡、LVS+Nginx）、缓存（Redis哨兵+分片）、数据库读写分离、消息中间件集群、池化技术（线程池/连接池） |
| **高可用** | N+1部署、集群容错、多机房容灾、故障转移、灰度发布、版本回滚 |
| **可扩展** | 水平拆分、业务拆分、稳定与易变分离、抽象化设计 |
| **数据安全** | 数据隔离、访问控制、传输加密、敏感数据脱敏 |
| **可监控** | 性能指标监控、日志采集（ELK）、链路追踪（Skywalking） |
