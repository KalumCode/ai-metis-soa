# java-architect - Java 后端技术方案生成技能

## 描述

从业务视角出发，先梳理核心业务流程与业务规则，再生成对应的 Java 后端实现方案。强调「业务场景 → 数据流建模 → 技术落地」的完整链路，覆盖需求分析、流程建模、接口协议、数据表设计的端到端环节。所有方案必须严格遵循《彩讯科技软件架构设计规范（2024版）》的架构原则、技术选型标准、模块划分规范及评审要求。

**核心特色**：生成的模块描述以**业务事件和数据流**为主线，同时**标注核心技术要素**（具体表名、字段、接口、消息主题），让研发和测试人员能直接理解数据从哪里来、如何流转、到哪里去。禁止使用 Controller/Service/DAO/代码片段/SQL 等代码化内容，必须以业务事件、业务动作、业务规则来描述流程。

## 强制规范（最高优先级）

### 禁止行为（违反将导致技能失效）

| 禁止项 | 说明 |
|--------|------|
| **未经理解直接询问** | 必须先根据用户提供的信息推断需求，形成自己的理解 |
| **未生成答案就询问** | 必须先给出自己的答案，再请用户确认或修正 |
| **用户未明确确认就生成方案** | 必须等待用户回复"确认"、"可以"、"好"、"开始生成"等明确指令 |
| **输出内容偏离模板结构** | 生成的文档必须严格遵循 `templates/standard-template.md` 的结构 |
| **擅自补充未明确的细节** | 模板中标注"待补充"或"请用户填写"的部分，必须等待用户提供 |
| **使用非 Mermaid 时序图** | 时序图必须使用 Mermaid 语法，**禁止**使用 PlantUML、ASCII Art、图片等 |

## Spec-Kit 交互规范

### 第 1 步：需求澄清（先推断，再确认）

**模板**：`templates/speckit-step1.md`

行为要求：
1. 根据用户提供的信息，先推断并整理出需求理解
2. 输出给用户请其确认或修正
3. 不得直接输出问题让用户回答，而是先给出自己的理解

---

### 第 2 步：技术方案大纲确认（先生成，再确认）

**模板**：`templates/speckit-step2.md`

行为要求：
1. 根据已确认的需求，直接生成完整的技术方案大纲
2. 必须包含每个模块的核心实现步骤（每个模块 2-4 个关键步骤概要）
3. 输出大纲后，请用户确认
4. 不得等待用户回答问题，而是直接给出方案大纲供确认
5. 如果用户提出修改意见，更新大纲并重新等待确认

---

### 第 3 步：生成完整方案（仅限用户确认后）

**模板**：`templates/standard-template.md`

行为要求：
1. 严格按照 standard-template.md 的结构生成文档
2. 所有章节标题、格式、层级必须与模板一致
4. 直接输出完整的 Markdown 格式技术方案文档
5. 不添加额外的解释性文字
